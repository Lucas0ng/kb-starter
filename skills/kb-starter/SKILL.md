# kb-starter · 建库与生长

把用户“一股脑塞进来”的零散资料变成分层知识库，并用回流和体检让它持续生长。脚本只做确定性的事（扫描、哈希、规则分类、复制、清单、机械检查）；需要理解内容的判断由你（AI）来做。

## 原则

- **主线由用户定，证据由 AI 填**：知识库为什么存在、有哪些项目、每个项目要回答什么问题，只有用户知道。建库先访谈，写成 `知识库纲要.md`；分项目、写总览、做体检都以纲要为准。你可以提议改纲要，不能擅自改。
- **原件只复制不移动**：用户的资料文件夹一个字节都不改。知识库里的 `00_原始资料/` 也是只读。
- **一个不漏**：来源里的每个文件在方案表里都有一行、一个去向和一条理由，读不了的也要列出来；apply 结束自动对账，对账不通过就不能说“完成了”。
- **整理完不乱**：旧版本进 `历史版本/`，同名文件保留来源文件夹，看不出内容的文件名可以起入库名（只改副本）；以后靠体检的“整洁度”一节防止重新变乱。
- **先出方案再动手**：建库和入库都先给用户看方案表，用户确认后才写入。
- **规则先行，AI 兜底**：文件名、扩展名、DOI、EXIF 能判断的交给脚本；判断不了的才由你读内容。这样几百个文件也不贵。
- **规则写进知识库**：分层规则、回流规则、体检和缺口自检提示词都生成在知识库里（`知识库说明.md`、`AGENTS.md`、`02_方法论库/`），换任何 AI 都能照着做，不依赖本 skill。
- **知识在卡片里，不在文件夹里**：整理好的原文只是材料。蒸馏成带「一句话 / 用于 / 来源」的卡片，才算知识库有了知识。
- **AI 的记忆是知识索引**：你没有跨对话的记忆。在这个知识库里工作时，开工先读 `知识索引.md`，靠每行的「用于」想起相关的卡片。
- **缺知识就记缺口，不凭空补**：发现缺少完成任务的知识时，记进缺口清单，告诉用户。
- **不编造**：总览、卡片里没有来源的内容写“待确认”。

## 脚本

`scripts/kb.py`，Python 3.9+，只用标准库。装了 `pdftotext`（poppler）时 PDF 识别更准，没有也能跑。下文 `KB` 指 `python3 <本 skill 目录>/scripts/kb.py`。

| 子命令 | 作用 |
|---|---|
| `KB scan <资料夹> --out <工作目录> [--kb <知识库>] [--outline 纲要]` | 扫描并生成 `plan.csv`、`plan.md`、`snippets.jsonl`；给了 `--kb` 会跳过已入库的文件，并自动读取 `<知识库>/知识库纲要.md`，按纲要里的项目名、别名和关键词把文件分到项目 |
| `KB decide <plan.csv> <decisions.json>` | 把你对“待AI”条目的判断写回方案表 |
| `KB apply <plan.csv> --kb <知识库> [--name 名称] [--dry-run]` | 复制入库；新库会自动建骨架、入口文件和模板；更新清单、资料索引、变更日志；最后自动对账，有问题退出码为 3 |
| `KB verify <plan.csv> --kb <知识库> [--full]` | 随时重新对账：来源里每个文件都有去向、副本与原件哈希一致、原件没被改过；`--full` 重算原件哈希 |
| `KB overview <知识库> [--project 名称]` | 生成项目总览草稿：目标、阶段、核心问题照抄纲要（标【你定】），资料概况、最近的记录、现行文件候选从清单整理（标【AI 整理】）；总览已存在时草稿写到 `99_工作区/总览草稿/`，不覆盖 |
| `KB index <知识库>` | 从卡片头部生成 `知识索引.md`（每张卡一行：一句话 · 用于 · 项目）；列出缺字段的卡片 |
| `KB gaps <知识库> [--out 文件]` | 缺口事实清单：还没蒸馏的原文、缺口清单待补项、被提到却没写的知识、没写来源的卡片、待测假设 |
| `KB stats <知识库> [--weeks 4]` | 增长统计：按周统计带标签的日志和新增卡片，给出“在生长 / 只在变大”的判断 |
| `KB lint <知识库> [--days 7]` | 体检事实清单：近期改动、断链、孤立笔记、候选概念、未登记文件、整洁度、增长 |
| `KB pack <知识库> [--project 名称]` | 生成网页版 AI 用的粘贴包 |

工作目录（方案表所在处）放在知识库外，例如系统临时目录或你的 scratchpad。

## 建库

用户说“帮我建知识库”“把这些资料整理一下”时：

1. **确定两个位置**：资料在哪个文件夹、知识库建在哪。用户已经说了就不问。
   - 用户在一个装满资料的文件夹里打开你、让你建知识库时（最常见的用法）：资料文件夹就是当前文件夹；知识库默认建在其中的 `知识库/` 子文件夹。这样所有写入都在工作区内，只能写当前文件夹的 agent 也能用；扫描会自动跳过 `知识库/` 本身，以后新资料继续丢进同一个文件夹即可。
   - 其他情况一次问完这两个问题；知识库默认 `~/知识库`，已经用 Obsidian 的话建议用它的 vault 路径。
   - 本 skill 是用户临时发链接让你下载的：仓库放在临时目录，写不了时放在当前文件夹的 `.kb-starter/` 下（以点开头的文件夹不会被当成资料）；方案表等过程文件也放那里。
2. **纲要访谈（扫描之前）**：知识库里已有 `知识库纲要.md` 就读它，跳过这一步。否则按 [references/纲要访谈.md](references/纲要访谈.md)：
   - 用户提到、或资料里能找到开题报告、申请书、任务书、汇报 PPT 这类“大纲材料”：直接从材料起草纲要，不用先问。
   - 没有：把细则里的五个问题一次发给用户，等回答。用户说“直接建，别问了”就不追问，起草一份只有项目名和关键词的最小纲要。
   - 按 `templates/root/知识库纲要.md` 的格式写到 `<知识库>/知识库纲要.md`（知识库文件夹还不存在就先建）。每个项目的「关键词」「别名」由你提，脚本靠它们分项目。
3. **扫描**：`KB scan <资料夹> --out <工作目录> --kb <知识库>`。知识库还不存在时也带上 `--kb`：知识库在资料文件夹里面时，靠它跳过知识库本身；纲要也从这里读取。
4. **处理待AI条目**：读 `snippets.jsonl` 里对应片段；片段不够就读原文首页（PDF 首页、docx 前几段、图片直接看）。判断类别和项目，写 `decisions.json`，再 `KB decide`。格式和判断要点见 [references/建库流程.md](references/建库流程.md)。
5. **定项目**：看 `plan.md` 末尾“识别到的项目”，以纲要为准。“不在纲要里的项目名”（多半是文件夹名）用 `rename_projects` 并入纲要里的项目；确实是纲要漏掉的新项目，在确认时问用户要不要加进纲要。还有很多“未分项目”的文件时，先补纲要关键词再扫一次，比逐条写 `项目` 省事。入库到已有知识库时，plan.md 会提醒“知识库里还没有这个项目，可能就是「X」”，优先并入已有项目。
6. **起入库名（可选）**：plan.md 的“文件名看不出内容的”一节列出 `IMG_4521.jpg`、`scan_0012.pdf` 这类文件。你看过内容、能确定是什么的，在 decisions.json 里给 `入库名`，格式 `YYYYMMDD_内容`（扩展名可省略，不能改）。只改知识库里的副本，原件和清单里的原名不变。看不出来的就不改。
7. **给用户确认（纲要和方案一起）**：一条消息里给两样东西。第一是纲要草稿：每个项目的目标、阶段、核心问题和关键词，标出“待确认”的地方。第二是方案：总数、各去向、需要用户扫一眼的“中/低置信度”条目、放进 `历史版本/` 的旧版本、改名入库的文件和“待定”条目，附 `plan.md` 路径。plan.md 顶部有“读不了的文件”时必须单独告诉用户（iCloud 未下载、没有权限），它们不会入库。用户改了纲要的项目或关键词，重新扫描后再确认。用户也可以直接改 `plan.csv`（Excel 能打开）。**没有确认不执行第 8 步。**
8. **执行并对账**：`KB apply <plan.csv> --kb <知识库> --name <名称>`。输出末尾是对账单；退出码 3 表示对账发现问题，把问题原样告诉用户，不要说“已完成”。
9. **写项目总览草稿**：`KB overview <知识库>`，为纲要里的每个项目生成 `<项目>_总览.md`。标【你定】的段落照抄纲要，不要改写；标【AI 整理】的段落由你补全：读“最近的记录”和“现行文件候选”里列出的文件，写“资料显示的进展”，从候选里选出现行文件、写清当前口径。资料和纲要说法不一致时（例如纲要说“第 1 轮做完”，资料里已有第 2 轮记录），写进“待确认”，不要自己改【你定】的段落。再把纲要里的核心问题加进 `假设台账.md`（状态“待测”）。
10. **更新导航**：在 `知识库导航.md` 的“当前项目”下每个项目写一行。
11. **第一轮蒸馏（用户同意后）**：建完的库只有材料没有知识，这一步决定它是不是“知识库”。先跑 `KB gaps`，从每个项目“还没蒸馏的原文”里挑最核心的 3–5 份，优先能回答纲要核心问题的（论文、会议纪要优先），按 [references/蒸馏流程.md](references/蒸馏流程.md) 写成卡片，再提 2–3 个概念节点，最后 `KB index`。耗时较多，先问用户要不要现在做、每个项目做几份。
12. **汇报**：知识库路径、各层文件数、对账结论（原样引用对账单第一行的等式）、读不了的文件、蒸馏了几张卡片、还有多少原文没蒸馏、哪些需要用户补充（总览里的“待确认”、09_待定），以及怎么在别的 AI 里用（见导航“换 AI 怎么办”）。请用户确认各总览的“现行执行文件”和“待确认”。

## 入库（新资料）

用户说“这些新文件入库”“我下载了几篇文献”时：`KB scan <新资料> --out <工作目录> --kb <知识库>`，之后同建库第 4–8 步（只需确认方案，纲要不变就不用再确认）。新资料属于纲要里没有的项目时，先问用户要不要把它加进纲要。知识库还没有纲要（例如不是用本 skill 建的库）时，入库前先建议做一次纲要访谈。入库完成后做**回流**：文献建卡片、实验记录按模板整理，并把 1–3 条可复用结论写进概念节点、更新假设台账。细则见 [references/入库与回流.md](references/入库与回流.md)。

用户手动把文件放进了 `00_原始资料/`：`KB scan <知识库>/00_原始资料 --out <工作目录> --kb <知识库>`，这些文件会被标成“登记”（只记入清单，不复制）。

## 蒸馏（把材料变成知识）

用户说“精读这篇”“把这次会议整理一下”“记下这个坑”，或入库、缺口自检后用户同意蒸馏时：

1. 按材料类型选模板：论文→文献卡片，会议/聊天/邮件里的决定→决策卡，故障和坑→问题卡，反复的操作→SOP，打交道的人→人物卡，复盘→教训卡，反复出现的概念→概念节点。模板在知识库的 `02_方法论库/写作模板/`。
2. 卡片头部必须填「一句话」「用于」「来源」。「用于」写场景（“设计添加剂浓度对照实验时”），不写主题（“添加剂”）。
3. 原文说的和你的判断分开写；数字带单位和条件；原文引用只用短句。
4. 回流：1–3 条会反复用到的结论写进概念节点；更新假设台账；补上的缺口在缺口清单里勾掉。
5. 日志追加 `[蒸馏] [[原文]] → [[卡片]]` 和 `[回流] …`，然后 `KB index`。

细则见 [references/蒸馏流程.md](references/蒸馏流程.md)。环境里有更专业的精读 skill 时可以用它写正文，但头部字段和“与我的工作的关系”“回流”两节必须补上。

## 知识索引：让你想得起来

在一个 kb-starter 知识库里接到任何依赖背景的任务时：

1. 先读根目录的 `知识索引.md`。每行是一张卡片：名字、一句话、用于什么场景、属于哪个项目。
2. 把当前任务和「用于」对上，打开相关卡片读细节；回答里写出用到了哪几张卡。
3. 卡片有新增或修改后，运行 `KB index` 重新生成。索引超过 12000 字会自动改用精简格式。

`KB index` 的末尾会列出缺「一句话」或「用于」的卡片；打开这些卡片时顺手补上。

## 缺口自检（让 AI 主动要知识）

**任务中**：发现缺少完成任务所需的知识时，不凭空补。在 `01_知识提炼/研究问题/缺口清单.md` 的“待补”下记一条（日期 · 缺什么 · 哪个任务需要 · 建议来源 · 补上后能回答什么），告诉用户，然后先用已有信息给出标“待确认”的结果。

**开始一件大事前**（用户说“看看还缺什么”“自检一下”，或要写论文某一节、设计新一轮实验、接手新项目）：

1. `KB gaps <知识库> --out <工作目录>/gaps.md`，拿到事实清单。
2. 按知识库里 `02_方法论库/AI提示词/缺口自检提示词.md` 的三类（有原文没蒸馏 / 库里没有要补资料 / 证据弱或矛盾），只列和用户目标相关的缺口，每类最多 5 条，写明“补上后哪个问题能回答得更好”。
3. 追加到缺口清单的“待补”，等用户勾选，再按蒸馏流程补。每补一条在日志记 `[缺口]`。

## 体检

用户说“体检”“看看知识库有什么问题”，或定时任务触发时：

1. `KB lint <知识库> --out <工作目录>/lint.md`。
2. 读事实清单和近期改动的笔记，按知识库里的 `02_方法论库/AI提示词/知识库体检提示词.md` 写报告到 `04_复盘日记/体检/YYYY-Www.md`。事实清单第 8 节“整洁度”（根目录多出的文件、待定区积压、过满文件夹、并存的多个版本、INBOX 积压）有内容时，报告里加一类“整理建议”。第 9 节“增长”末尾的判断句原样写在报告开头；提示索引过期时，体检后运行 `KB index`。第 10 节“纲要对照”有内容时（项目很久没动、资料里出现纲要外的项目、纲要很久没更新），报告里加一类“纲要更新建议”：只提议，用户勾选后才改纲要，并在纲要的「修订记录」记一行。
3. 报告只提建议。用户勾选后说“执行体检”，你只执行被勾选的条目。

细则见 [references/体检流程.md](references/体检流程.md)。用户想每周自动跑，可以用宿主的定时任务功能（如 Claude 的 scheduled tasks、cron）每周触发一次体检。

用户问“知识库有没有在长”“最近积累了多少”时：`KB stats <知识库>`，把表格和判断句给用户。

## 粘贴包

用户要在网页版 ChatGPT、豆包、DeepSeek 等里用知识库时：先 `KB index`，再 `KB pack <知识库> [--project 名称]`，告诉用户文件路径，整份粘贴过去即可。粘贴包包含纲要、导航、项目总览、假设台账和知识索引。

## 什么时候停下来问

- 建库扫描前：没有大纲材料、也没有纲要时，先发访谈问题（一轮问完）。
- 方案表执行前（必须），纲要草稿和方案一起确认。
- 想改纲要的目标、核心问题或增删项目时：只提议，用户同意才改。
- 知识库路径已存在且不是空文件夹、也不是 kb-starter 建的库（没有 `.kb/`）：问用户是并入还是另建。只有一份你刚写的 `知识库纲要.md` 的文件夹算空文件夹。
- 待AI条目超过 50 个：先问用户是逐个判断，还是先全部放进 `09_待定` 以后再说（`apply --pending-to-unsorted`）。
- 发现疑似隐私文件（证件、合同、银行流水、密码表）：列出来问用户是否入库。
- 有“无法读取”的文件：告诉用户原因和处理办法（iCloud 先下载、权限问题先改权限），处理后重新扫描。
- 对账不通过（apply 或 verify 退出码 3）：停下，把对账单里的问题原样告诉用户。
